# Проверка работающей установки

Выполняйте проверки после установки [туннелей и WARP](exit.md) и [маршрутизации на РФ](ru.md). Живой тест удобнее делать с отдельного устройства с обычным клиентским профилем. Для сравнения используйте новые соединения: направление уже начатого потока закреплено в conntrack.

## 1. Проверить каналы до переключения клиентов

На каждом узле выполните:

```sh
ip -br -4 addr show dev rn-ipip
ip -br -4 addr show dev rn-gre
ip tunnel show rn-ipip
ip tunnel show rn-gre
ip nexthop get id 65100
sysctl net.ipv4.fib_multipath_hash_policy
```

На РФ адреса туннелей оканчиваются на `.1`, на зарубежном узле — на `.2`. В группе `65100` должны быть оба участника, `65101` и `65102`, с равными весами. Значение `fib_multipath_hash_policy = 1` включает учёт транспортных портов. Если интерфейсы подняты, но полезный трафик не проходит, сверяйте `local` и `remote` на обоих концах, правила фильтрации протоколов 4/47 и счётчики `ip -s link show dev rn-ipip` / `rn-gre`.

На зарубежном узле проверьте собственный маршрут и оба варианта выхода:

```sh
ip -4 route show default
wg show exit-warp latest-handshakes
curl --noproxy '*' -4fsS --max-time 8 --interface exit-warp https://1.1.1.1/cdn-cgi/trace | grep -E '^(ip|warp)='
curl --noproxy '*' -4fsS --max-time 8 https://1.1.1.1/cdn-cgi/trace | grep -E '^(ip|warp)='
nft list set ip exit_transit warp_ingress
```

Первая проверка `curl` должна показать `warp=on` или `warp=plus`, вторая — обычный публичный адрес зарубежного узла. При доступном WARP в `warp_ingress` появятся `rn-ipip` и `rn-gre`. Внешний адрес Cloudflare может меняться.

## 2. Проверить DNS с устройства клиента

Примеры рассчитаны на `dig` и DNS-адрес профиля `172.29.172.254`.

```sh
dig @172.29.172.254 ya.ru A
dig @172.29.172.254 example.org A +tcp
dig @172.29.172.254 cloudflare.com AAAA +noall +comments +answer
dig @172.29.172.254 cloudflare.com HTTPS +short
dig @172.29.172.254 _dns.dns.google SVCB +tcp +short
```

У первых двух запросов ожидается IPv4-ответ. В ответе AAAA — `status: NOERROR` и `ANSWER: 0`. В HTTPS/SVCB отсутствует `ipv6hint`, сохраняются остальные разрешённые параметры. Наличие `ipv4hint` зависит от того, опубликовал ли его владелец домена.

Чтобы подтвердить выбор DNS-провайдера, наблюдайте запросы при пустом кэше или используйте новое имя в нужной зоне. Запрашивайте имена по очереди. Внешний канал зашифрован, поэтому сопоставляйте время запроса, направление и адрес назначения.

- На внешнем интерфейсе РФ должны появиться соединения на TCP/853 к `77.88.8.8` или `77.88.8.1` для имён из `CATEGORY-RU`.
- Для обычного внешнего домена на мосту Amnezia виден обмен контейнера Unbound с `1.1.1.1:853` или `1.0.0.1:853`. Пакеты уходят через `rn-ipip` или `rn-gre`; на зарубежном узле видны на `exit-warp`. Сниффер запускайте до запроса и ограничивайте его адресом/портом и числом пакетов.
- Выбранный адрес из ответа на `ya.ru A` можно проверить на РФ командой `nft get element inet awg_geo ru_dns_a '{ АДРЕС }'` и такой же командой для `ru_dns_b`. Подставьте фактический IPv4. Сразу после нового ответа адрес должен находиться в обоих наборах.

## 3. Проверить настоящий маршрут

На РФ снимите счётчики до и после каждой попытки:

```sh
for c in geo_ru_net geo_ru_dns geo_exit geo_ru_fallback; do
    sudo nft list counter inet awg_geo "$c"
done
```

С клиента проверяйте три разных случая:

| Тест | Что считать успехом |
|---|---|
| Соединение к адресу из `GeoIP:RU` без DNS-запроса | Увеличился `geo_ru_net`; соединение вышло по внешнему интерфейсу РФ |
| Запрос к имени из `CATEGORY-RU` с адресом вне `GeoIP:RU`, затем соединение с этим IP | Адрес появился в DNS-наборах, увеличился `geo_ru_dns`; соединение вышло из РФ |
| Соединение к публичному адресу вне обоих наборов | Увеличился `geo_exit`; пакет виден на одном из двух туннелей |

Для первого случая можно использовать `curl --resolve "ИМЯ:443:АДРЕС" "https://ИМЯ/"` с адресом из текущей базы. Для второго подберите имя по текущему `geosite/current/rules.txt`: проверьте фактический A-ответ и отсутствие IP в `ru_nets`. Классификация по IP имеет приоритет над DNS-наборами.

С клиента и с самого узла РФ выполните:

```sh
dig @1.1.1.1 whoami.cloudflare CH TXT +short
dig @1.0.0.1 whoami.cloudflare CH TXT +tcp +short
curl --noproxy '*' -4fsS --max-time 8 https://1.1.1.1/cdn-cgi/trace | grep -E '^(ip|warp)='
```

При исправных каналах ожидается выход WARP. На РФ `ip route get 1.1.1.1` без марки выводит путь до обработки пакета цепочкой nftables `output`. Доставку подтверждайте фактическим DNS/HTTPS-ответом и трафиком в туннеле. Для проверки ECMP откройте несколько десятков новых соединений с разными исходными портами и сравните счётчики обоих интерфейсов; небольшая выборка может распределиться не поровну.

## 4. Проверить автоматическое переключение

Проводите испытания на выделенной установке или в согласованное окно. Временно блокируйте **только контрольные запросы** выбранного пути, а затем снимайте временное правило. На РФ для проб используются метки `0x41570101` (IPIP) и `0x41570102` (GRE), адрес `1.1.1.1`, TCP/443. На зарубежном узле тест WARP обращается к Cloudflare с привязкой к `exit-warp`.

| Состояние | Ожидаемый результат нового запроса клиента к Cloudflare |
|---|---|
| Недоступна проверка только IPIP | РФ выбирает `65102`, запрос проходит через GRE |
| Недоступна проверка только GRE | РФ выбирает `65101`, запрос проходит через IPIP |
| Недоступны обе проверки на РФ | Запрос получает обычный публичный адрес РФ |
| Доступен зарубежный узел, не проходит проверка WARP | Запрос получает публичный адрес зарубежного узла |
| Проверки восстановлены | Новый запрос показывает `warp=on` или `warp=plus`, возвращается группа `65100` |

На РФ смотрите `cat /run/awg-geo/health.json`, `ip -4 route show table 61570` и `journalctl -u awg-geo-health.service -n 20`. На зарубежном узле — `journalctl -u exit-health.service -n 20` и `nft list set ip exit_transit warp_ingress`.

## 5. Проверить обновления и автозапуск

```sh
# На узле РФ
systemctl list-timers awg-geo-update.timer awg-geo-health.timer awg-geo-reconcile.timer
journalctl -u awg-geo-update.service -n 20 --no-pager
cat /var/lib/awg-geo/geoip/current/metadata.json
cat /var/lib/awg-geo/geosite/current/metadata.json
```

Сценарий обновления проверяет первичный релиз, SHA-256, разбор и наличие нужной категории. В изолированном тесте переберите четыре варианта: обе базы корректны, пуст только GeoIP, пуст только GeoSite, пусты обе. Для каждого смотрите хеши файлов и фактические совпадения в DNS и nftables. При ошибке GeoSite оба накопленных DNS-набора сохраняются. Команды запуска тестов см. в [руководстве РФ](ru.md).

Для проверки холодного старта перезагружайте узлы по очереди в согласованное окно. После загрузки зарубежного узла дождитесь восстановления WARP и обоих путей с РФ. После загрузки российского узла проверьте контейнеры Amnezia, оба пути в `health.json`, службу DNS, таймеры и повторите клиентские запросы. Системный маршрут по умолчанию обоих узлов по-прежнему должен указывать на их собственный внешний интерфейс.
